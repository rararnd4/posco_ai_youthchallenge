# 코드 검토 결과와 다음 작업

원본을 보존하기 위해 아래 문제는 코드에 직접 수정하지 않고 기록만 했습니다.

## 실행을 막는 항목

1. **서보 추적 함수 호출 조건을 수정했습니다.**
   원본은 길이가 2인 `boxMiddle`을 `len(boxMiddle) == 1`로 검사해 호출되지 않았습니다. 저장소의 핵심 코드는 탐지된 중심 좌표로 `servoMove()`를 바로 호출하도록 정리했습니다.

2. **YOLOv7 통합 코드에서 Arduino 연결이 꺼져 있습니다.**
   시리얼 포트 생성과 `arduinoWrite` 스레드 실행 부분이 주석 처리되어 있습니다. 함수 안에서는 `arduino` 객체를 사용하므로 일부만 주석 해제하면 `NameError`가 발생할 수 있습니다.

3. **클래스 파일을 모델 폴더에 배치했습니다.**
   Drive의 별도 학습 폴더에서 확인한 단일 클래스 구성을 바탕으로 `model/obj.names`를 함께 두었습니다. 실제 학습 파일과 동일한 내용인지는 실행 전에 확인해야 합니다.

4. **모델 상대 경로를 저장소 기준으로 수정했습니다.**
   핵심 Python 코드는 실행 위치와 관계없이 루트의 `model/`에서 cfg, weights, 클래스 파일을 읽습니다.

## 동작 안정성 문제

1. 탐지 스레드와 화면 표시 루프가 전역 리스트를 공유합니다. 새 리스트로 한 번에 교체해 인덱스 오류를 줄이려는 처리는 있지만 명시적인 동기화는 없습니다.
2. 프로그램 종료 때 카메라 `release`, OpenCV 창 종료, pigpio 연결 종료 처리가 없습니다.
3. Arduino의 `serialData`는 새 값이 들어올 때까지 유지됩니다. `detected` 이후 `not-detected`가 전달되지 않으면 탐지 상태가 계속 남을 수 있습니다.
4. 초음파 거리 측정의 `pulseIn`에 제한 시간이 없어 센서 응답이 없을 때 루프가 지연될 수 있습니다.
5. DFPlayer 초기화 성공 여부를 확인하지 않아 배선이나 SD 카드 오류를 구분하기 어렵습니다.

## 데이터 분석 관점에서 추가하면 좋은 기록

- 학습·검증·테스트 데이터 수와 분할 기준
- 원본 이미지 수와 Pillow 증강 후 이미지 수
- 클래스 불균형, 촬영 거리, 조명, 배경별 표본 수
- mAP 계산 기준(`mAP@0.5` 또는 `mAP@0.5:0.95`)과 평가 데이터 고정 여부
- YOLOv3-tiny와 YOLOv7-tiny의 동일 조건 비교표
- Raspberry Pi에서의 FPS, 평균 추론 시간, CPU 사용률
- 실내 이미지와 실제 유리창 환경의 탐지율·오탐률 비교

## 권장 수정 순서

1. Raspberry Pi에서 영상 추론을 재현하고 `obj.names` 내용을 실제 학습 파일과 대조
2. 수정된 서보 호출과 각도 변화 범위를 실제 장치에서 시험
3. Arduino 시리얼 송수신을 다시 연결하고 메시지 끝 문자를 명확히 정의
4. 탐지 신호의 유지 시간과 음원 재생 시간을 상태 머신으로 정리
5. 고정된 테스트 영상으로 탐지율, 오탐률, FPS를 기록
6. 현장 환경에서 같은 지표를 다시 측정해 차이를 분석
